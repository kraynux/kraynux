# Архитектура проекта — Clean Architecture

Этот документ объясняет, как организован проект, почему была выбрана такая организация и что содержит каждая папка. Он предназначен как для посетителей, которые хотят понять общий принцип работы приложения, так и для разработчиков, которые хотят участвовать в его разработке или поддерживать его.

Приложение следует принципам **Clean Architecture**: ядро программного обеспечения изолировано от технических деталей, пользовательских интерфейсов и внешних зависимостей. Такое разделение делает проект более читаемым, тестируемым, поддерживаемым и простым в развитии.

---

## 1. Общий принцип

Приложение разделено на слои, каждый из которых имеет определённую роль.

Основная идея проста:

```text
Интерфейс запрашивает выполнение действия.
Приложение координирует это действие.
Домен применяет бизнес-правила.
Порты определяют, что необходимо приложению.
Инфраструктура предоставляет конкретные реализации.
```

Благодаря этому важная логика проекта не зависит напрямую от:

- терминала;
- графического интерфейса;
- базы данных;
- сети;
- файловой системы;
- внешней библиотеки;
- системного инструмента.

Такая независимость позволяет заменить часть программы, не переписывая всё остальное.

---

## 2. Общий обзор

```text
[НАЗВАНИЕ_ПРОЕКТА]/
└── src/
    └── [название_проекта]/
        ├── app/              Запуск, жизненный цикл и внедрение зависимостей
        ├── core/             Сквозные возможности, перечисления и исключения
        ├── domain/           Чистая бизнес-логика
        ├── application/      Варианты использования: commands и queries
        ├── infrastructure/   Бэкенды, хранилище, экспорт, журналы, системные зонды…
        ├── ports/            Контракты Protocol / ABC
        ├── interfaces/       CLI и TUI
        ├── plugins/          Встроенные расширения
        └── shared/           Разбор, сеть, форматирование и сквозные утилиты
```

---

## 3. Схема зависимостей

Зависимости всегда должны идти в одном направлении:

```text
interfaces
    ↓
application
    ↓
domain
    ↑
ports
    ↑
infrastructure
```

На практике:

- `interfaces/` может вызывать `application/`.
- `application/` может вызывать `domain/` и использовать контракты из `ports/`.
- `domain/` не зависит ни от `application/`, ни от `infrastructure/`, ни от `interfaces/`.
- `infrastructure/` реализует контракты, определённые в `ports/`.
- `app/` собирает слои и предоставляет необходимые зависимости.

Основное правило:

> Домен никогда не знает об инфраструктуре.  
> Инфраструктура знает о портах, но домен не знает об инфраструктуре.

---

## 4. Папка `app/`

### Роль

Папка `app/` является **точкой сборки** приложения.

Она содержит:

- запуск программы;
- жизненный цикл;
- контейнер внедрения зависимостей;
- создание объектов, необходимых для работы;
- выбор конкретных реализаций;
- инициализацию конфигурации;
- связывание слоёв между собой.

### Пример обязанностей

```text
app/
├── bootstrap.py
├── container.py
└── lifecycle.py
```

| Файл | Роль |
|---|---|
| `bootstrap.py` | Запускает приложение и выбирает интерфейс для запуска |
| `container.py` | Создаёт и связывает зависимости |
| `lifecycle.py` | Управляет запуском, остановкой и очисткой |

### Правило

`app/` не содержит бизнес-логики.

Он не решает:

- что является бизнес-правилом;
- как должны вычисляться данные;
- как должен анализироваться запрос;
- как должен экспортироваться файл.

Он только собирает существующие компоненты.

---

## 5. Папка `core/`

### Роль

Папка `core/` содержит **сквозной словарь проекта**.

Она объединяет элементы, используемые несколькими слоями, но не являющиеся сами по себе бизнес-правилами.

Она может содержать:

- возможности;
- перечисления;
- константы;
- сквозные исключения;
- общие типы;
- информацию о платформе;
- определения уровней или состояний.

### Пример

```text
core/
├── capabilities.py
├── constants.py
├── enums.py
└── exceptions.py
```

| Файл | Роль |
|---|---|
| `capabilities.py` | Описывает доступные или активируемые возможности |
| `constants.py` | Содержит константы проекта |
| `enums.py` | Определяет возможные состояния, типы или уровни |
| `exceptions.py` | Определяет сквозные ошибки |

### Правило

`core/` должен оставаться лёгким и стабильным.

Он не должен содержать:

- сложную бизнес-логику;
- сетевые вызовы;
- доступ к диску;
- пользовательский интерфейс;
- прямые зависимости от внешних библиотек.

---

## 6. Папка `domain/`

### Роль

Папка `domain/` является **ядром проекта**.

Она содержит чистую бизнес-логику: правила, концепции и вычисления, которые действительно определяют, что делает приложение.

Она может содержать:

- сущности;
- объекты-значения;
- политики;
- бизнес-правила;
- сервисы домена;
- вычисления;
- бизнес-валидации;
- модели бизнес-данных.

### Пример

```text
domain/
├── entities/
├── value_objects/
├── policies/
└── services/
```

| Элемент | Роль |
|---|---|
| Сущность | Бизнес-объект, имеющий идентичность |
| Объект-значение | Неизменяемое и проверенное значение |
| Политика | Переиспользуемое бизнес-правило |
| Сервис домена | Бизнес-логика, которая не принадлежит одной сущности |

### Строгие правила

Папка `domain/`:

- не обращается к диску;
- не выполняет сетевых вызовов;
- не выполняет системные команды;
- не обращается к базе данных;
- не импортирует пользовательский интерфейс;
- не импортирует инфраструктуру;
- не зависит от внешней технической библиотеки, если этого можно избежать.

Домен должен быть тестируемым без сервера, файлов, сети и интерфейса.

---

## 7. Папка `application/`

### Роль

Папка `application/` координирует варианты использования.

Она отвечает на вопрос:

> «Что происходит, когда пользователь запрашивает это действие?»

Она содержит:

- commands;
- queries;
- варианты использования;
- координаторы;
- обработчики действий;
- координацию между доменом и портами.

### Различие между commands и queries

| Тип | Цель | Изменяет данные |
|---|---|---|
| Command | Выполнить действие | Да |
| Query | Прочитать или вычислить информацию | Нет |

Примеры:

| Command | Query |
|---|---|
| Применить конфигурацию | Прочитать текущую конфигурацию |
| Запустить анализ | Получить результат анализа |
| Экспортировать отчёт | Перечислить доступные элементы |
| Очистить данные | Просмотреть историю |

### Пример

```text
application/
├── commands/
│   ├── apply_config.py
│   └── export_report.py
└── queries/
    ├── get_status.py
    └── list_items.py
```

### Правило

`application/` не содержит:

- вывода в терминал;
- интерфейса Textual;
- команд Rich;
- прямого доступа к базе данных;
- прямых вызовов внешних инструментов.

Он координирует, но не реализует технические детали.

---

## 8. Папка `ports/`

### Роль

Папка `ports/` определяет **контракты**, ожидаемые приложением.

Порт описывает, **что необходимо приложению**, не предписывая, как это должно быть реализовано.

Обычно он содержит:

- определения `Protocol`;
- абстрактные классы `ABC`;
- интерфейсы репозиториев;
- интерфейсы экспорта;
- интерфейсы зондов;
- интерфейсы внешних сервисов;
- интерфейсы хранилищ.

### Пример

```text
ports/
├── repositories.py
├── exporters.py
├── probes.py
└── storage.py
```

| Порт | Роль |
|---|---|
| `Repository` | Чтение или сохранение данных |
| `Exporter` | Создание вывода в заданном формате |
| `Probe` | Сбор системной или сетевой информации |
| `Storage` | Управление механизмом хранения |

### Концептуальный пример

```python
class ReportExporter(Protocol):
    def export(self, report: Report, destination: Path) -> None:
        ...
```

Этот контракт говорит:

> «Приложению нужен объект, способный экспортировать отчёт».

Он не говорит:

- будет ли экспорт в формате Markdown;
- будет ли экспорт в формате JSON;
- будет ли файл записан локально;
- будет ли экспорт отправлен по сети.

Эти решения относятся к `infrastructure/`.

### Правило

Порты — это контракты, а не реализации.

Они не должны содержать:

- сложную бизнес-логику;
- доступ к диску;
- сетевые вызовы;
- конкретные реализации;
- прямые зависимости от внешних библиотек.

---

## 9. Папка `infrastructure/`

### Роль

Папка `infrastructure/` содержит **конкретные реализации** портов.

Это слой, который взаимодействует с внешним миром.

Она может содержать:

- доступ к файлам;
- доступ к базе данных;
- экспорт в Markdown, JSON, CSV или другие форматы;
- журналирование;
- сетевые вызовы;
- системные зонды;
- контролируемое выполнение внешних инструментов;
- адаптеры для сторонних библиотек;
- реализации репозиториев;
- реализации хранилищ.

### Пример

```text
infrastructure/
├── storage/
│   ├── sqlite_repository.py
│   └── json_file_repository.py
├── export/
│   ├── markdown_exporter.py
│   └── json_exporter.py
├── system/
│   ├── process_probe.py
│   └── filesystem_probe.py
└── logging/
    └── structured_logger.py
```

| Элемент | Роль |
|---|---|
| `sqlite_repository.py` | Реализует репозиторий с использованием SQLite |
| `json_file_repository.py` | Реализует репозиторий с использованием файлов JSON |
| `markdown_exporter.py` | Экспортирует отчёт в Markdown |
| `json_exporter.py` | Экспортирует отчёт в JSON |
| `process_probe.py` | Собирает информацию о процессах |
| `filesystem_probe.py` | Собирает информацию о файловой системе |
| `structured_logger.py` | Создаёт структурированные журналы |

### Правило

`infrastructure/` — единственный слой, которому разрешено напрямую обращаться к:

- файловой системе;
- сети;
- SQLite;
- внешним библиотекам;
- системным инструментам;
- подпроцессам, когда это необходимо и контролируется.

Такая централизация облегчает:

- тестирование;
- аудит безопасности;
- замену бэкенда;
- ограничение побочных эффектов.

---

## 10. Папка `interfaces/`

### Роль

Папка `interfaces/` содержит точки входа, видимые пользователю.

Она чётко разделяет:

- CLI;
- TUI;
- возможные будущие веб- или API-интерфейсы.

### Структура

```text
interfaces/
├── cli/
│   ├── main.py
│   ├── commands/
│   └── rendering/
└── tui/
    ├── app.py
    ├── screens/
    └── widgets/
```

| Интерфейс | Технология | Роль |
|---|---|---|
| `cli/` | Rich | Интерфейс командной строки |
| `tui/` | Textual | Интерактивный терминальный интерфейс |

### CLI

CLI — это интерфейс командной строки.

Он позволяет:

- запускать приложение;
- выполнять конкретное действие;
- отображать результат;
- автоматизировать задачу;
- интегрировать инструмент в сценарий;
- использовать приложение удалённо через SSH.

### TUI

TUI — это интерактивный терминальный интерфейс.

Он позволяет:

- перемещаться по функциям;
- просматривать информацию;
- выполнять действия;
- просматривать результаты;
- использовать приложение, не запоминая все команды.

### Правило

Интерфейсы не содержат бизнес-логики.

Они:

- получают намерение пользователя;
- вызывают вариант использования в `application/`;
- отображают результат;
- переводят ошибки в понятные сообщения.

Они не должны:

- напрямую вызывать инфраструктуру;
- запускать подпроцессы;
- напрямую обращаться к файлам;
- содержать бизнес-правила;
- дублировать логику из `application/`.

---

## 11. Папка `plugins/`

### Роль

Папка `plugins/` предназначена для **встроенных расширений**.

Она позволяет добавлять функции без перегрузки ядра проекта.

Например, плагин может:

- добавить формат экспорта;
- добавить зонд;
- добавить команду;
- добавить экран в TUI;
- добавить внешнюю интеграцию;
- добавить необязательную возможность.

### Принцип

Плагин должен соблюдать те же правила, что и остальная часть проекта:

- он не обходит порты;
- он не изменяет напрямую домен;
- он предоставляет свои функции через понятные контракты;
- он остаётся отключаемым без нарушения работы приложения.

### Возможная структура

```text
plugins/
└── [имя_плагина]/
    ├── __init__.py
    ├── manifest.py
    ├── application/
    ├── infrastructure/
    └── interfaces/
```

### Правило

Плагин — это расширение, а не лазейка.

Он должен следовать общей архитектуре и не должен создавать циклические зависимости с ядром проекта.

---

## 12. Папка `shared/`

### Роль

Папка `shared/` содержит сквозные утилиты, которые не относятся ни к домену, ни к приложению, ни к инфраструктуре.

Она объединяет переиспользуемые универсальные функции.

Она может содержать:

- разбор данных;
- сетевые утилиты;
- форматирование;
- обработку текста;
- помощники для работы с датами;
- помощники для работы с путями;
- универсальные утилиты валидации;
- помощники для сериализации.

### Пример

```text
shared/
├── parsing/
├── network/
├── formatting/
└── utils/
```

| Папка | Роль |
|---|---|
| `parsing/` | Разбор текста, JSON, YAML и других форматов |
| `network/` | Универсальные сетевые утилиты |
| `formatting/` | Форматирование значений, дат, размеров или таблиц |
| `utils/` | Сквозные вспомогательные функции |

### Правило

`shared/` не должен превращаться в папку-свалку.

Утилита помещается в `shared/` только если она:

- переиспользуема;
- универсальна;
- независима от конкретного сценария использования;
- полезна для нескольких слоёв.

---

## 13. Сводка обязанностей

| Папка | Основная роль | Может зависеть от | Не должна зависеть от |
|---|---|---|---|
| `app/` | Собирать и запускать приложение | Все слои | — |
| `core/` | Словарь, константы, перечисления и исключения | `shared/`, если необходимо | `infrastructure/`, `interfaces/` |
| `domain/` | Чистая бизнес-логика | `core/` | `application/`, `infrastructure/`, `interfaces/` |
| `application/` | Координировать варианты использования | `domain/`, `ports/`, `core/` | `infrastructure/`, `interfaces/` |
| `ports/` | Определять контракты | `domain/`, если необходимо | `infrastructure/`, `interfaces/` |
| `infrastructure/` | Реализовывать порты и взаимодействовать с внешним миром | `ports/`, `domain/`, `core/`, `shared/` | `interfaces/` |
| `interfaces/` | Взаимодействовать с пользователем | `application/`, `core/` | Напрямую от `infrastructure/` |
| `plugins/` | Добавлять расширения | В зависимости от типа расширения | Обход архитектуры |
| `shared/` | Сквозные утилиты | Нет бизнес-слоёв | Конкретная бизнес-логика |

## 14. Пример прохождения действия

Рассмотрим пример, когда пользователь запрашивает экспорт отчёта в Markdown.

```text
1. Пользователь выполняет команду CLI.

2. interfaces/cli/
   Получает команду и её параметры.

3. interfaces/cli/
   Вызывает соответствующий вариант использования в application/.

4. application/
   Проверяет намерение и подготавливает действие.

5. application/
   Использует домен для создания или проверки отчёта.

6. application/
   Запрашивает экспорт через порт ReportExporter.

7. infrastructure/
   Предоставляет реализацию MarkdownExporter.

8. infrastructure/
   Записывает файл Markdown на диск.

9. interfaces/cli/
   Отображает результат пользователю.
```

Упрощённая схема:

```text
CLI
 ↓
Application
 ↓
Domain
 ↓
Порт Exporter
 ↓
Markdown-инфраструктура
 ↓
Файл Markdown
```

## 15. Почему выбрана эта архитектура?

### Читаемость

Каждая папка имеет одну роль, поэтому легче найти, где добавить или исправить функцию.

### Тестируемость

Домен можно тестировать без интерфейса, базы данных и доступа к сети.

### Поддерживаемость

Изменение интерфейса, хранилища или внешнего инструмента не должно требовать переписывания бизнес-логики.

### Безопасность

Чувствительные обращения — к файлам, сети, подпроцессам и базам данных — сосредоточены в `infrastructure/`. Это упрощает их аудит и контроль.

### Развиваемость

Можно добавить:

- новый интерфейс;
- новый формат экспорта;
- новый бэкенд хранилища;
- новый плагин;
- новый системный зонд;

без изменения бизнес-ядра.

### Переносимость

Приложение может развиваться в сторону других сред, систем или режимов взаимодействия, не будучи привязанным к конкретной технологии.
