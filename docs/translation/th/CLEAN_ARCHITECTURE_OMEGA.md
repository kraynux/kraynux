เอกสารนี้อธิบายว่าโปรเจกต์ถูกจัดระเบียบอย่างไร เหตุใดจึงเลือกการจัดระเบียบแบบนี้ และแต่ละโฟลเดอร์มีอะไรอยู่บ้าง เอกสารนี้เขียนขึ้นทั้งสำหรับผู้เยี่ยมชมที่ต้องการเข้าใจการทำงานของแอปพลิเคชัน และสำหรับนักพัฒนาที่ต้องการมีส่วนร่วมหรือดูแลรักษาโปรเจกต์

แอปพลิเคชันนี้ใช้ **Clean Architecture**: แกนหลักของซอฟต์แวร์ถูกแยกออกจากรายละเอียดทางเทคนิค อินเทอร์เฟซผู้ใช้ และการพึ่งพาภายนอก การแยกนี้ทำให้โปรเจกต์อ่าน ทดสอบ ดูแล และพัฒนาต่อได้ง่ายขึ้น

---

## 1. หลักการทั่วไป

แอปพลิเคชันถูกแบ่งออกเป็นเลเยอร์ แต่ละเลเยอร์มีบทบาทที่ชัดเจน

แนวคิดหลักนั้นเรียบง่าย:

```text
อินเทอร์เฟซร้องขอการกระทำ
แอปพลิเคชันประสานงานการกระทำนั้น
โดเมนใช้กฎทางธุรกิจ
พอร์ตกำหนดสิ่งที่แอปพลิเคชันต้องการ
โครงสร้างพื้นฐานให้การใช้งานจริง (implementation)
```

ด้วยเหตุนี้ ตรรกะสำคัญของโปรเจกต์จึงไม่ขึ้นตรงกับ:

- เทอร์มินัล;
- อินเทอร์เฟซกราฟิก;
- ฐานข้อมูล;
- เครือข่าย;
- ระบบไฟล์;
- ไลบรารีภายนอก;
- เครื่องมือของระบบ

ความเป็นอิสระนี้ทำให้สามารถเปลี่ยนส่วนหนึ่งของซอฟต์แวร์ได้โดยไม่ต้องเขียนส่วนที่เหลือใหม่ทั้งหมด

---

## 2. ภาพรวม

```text
[PROJECT_NAME]/
└── src/
    └── [project_name]/
        ├── app/              การเริ่มต้นระบบ วงจรชีวิต และการฉีดการพึ่งพา
        ├── core/             ความสามารถ enum และข้อยกเว้นที่ใช้ร่วมกัน
        ├── domain/           ตรรกะทางธุรกิจล้วน
        ├── application/      กรณีการใช้งาน: commands และ queries
        ├── infrastructure/   แบ็กเอนด์ การจัดเก็บ การส่งออก ล็อก โพรบระบบ…
        ├── ports/            สัญญา Protocol / ABC
        ├── interfaces/       CLI และ TUI
        ├── plugins/          ส่วนขยายที่ติดมาในตัว
        └── shared/           การแยกวิเคราะห์ เครือข่าย การจัดรูปแบบ และยูทิลิตีที่ใช้ร่วมกัน
```

---

## 3. แผนภาพการพึ่งพา

การพึ่งพาต้องไปในทิศทางเดียวกันเสมอ:

```text
interfaces
    ↓
application
    ↓
domain
    ↑
ports
    ↑
infrastructure
```

ในทางปฏิบัติ:

- `interfaces/` สามารถเรียก `application/` ได้
- `application/` สามารถเรียก `domain/` และใช้สัญญาที่กำหนดไว้ใน `ports/` ได้
- `domain/` ไม่พึ่งพา `application/`, `infrastructure/` หรือ `interfaces/`
- `infrastructure/` ทำ implementation ของสัญญาที่กำหนดไว้ใน `ports/`
- `app/` ประกอบเลเยอร์เข้าด้วยกันและจัดหาการพึ่งพาที่จำเป็น

กฎสำคัญ:

> โดเมนไม่เคยรู้จักโครงสร้างพื้นฐาน  
> โครงสร้างพื้นฐานรู้จักพอร์ต แต่โดเมนไม่รู้จักโครงสร้างพื้นฐาน

## 4. โฟลเดอร์ `app/`

### บทบาท

โฟลเดอร์ `app/` คือ **จุดประกอบ** ของแอปพลิเคชัน

ภายในประกอบด้วย:

- การเริ่มต้นแอปพลิเคชัน;
- วงจรชีวิต;
- คอนเทนเนอร์สำหรับฉีดการพึ่งพา;
- การสร้างออบเจกต์ที่จำเป็นต่อการทำงาน;
- การเลือก implementation ที่ใช้จริง;
- การเริ่มต้นการตั้งค่า;
- การเชื่อมต่อระหว่างเลเยอร์

### ตัวอย่างหน้าที่

```text
app/
├── bootstrap.py
├── container.py
└── lifecycle.py
```

| ไฟล์ | บทบาท |
|---|---|
| `bootstrap.py` | เริ่มแอปพลิเคชันและเลือกอินเทอร์เฟซที่จะเปิด |
| `container.py` | สร้างและเชื่อมการพึ่งพา |
| `lifecycle.py` | จัดการการเริ่มต้น การหยุด และการเก็บกวาด |

### กฎ

`app/` ไม่มีตรรกะทางธุรกิจ

มันไม่ตัดสินใจว่า:

- กฎทางธุรกิจคืออะไร;
- ข้อมูลหนึ่งต้องคำนวณอย่างไร;
- คำขอหนึ่งต้องวิเคราะห์อย่างไร;
- ไฟล์หนึ่งต้องส่งออกอย่างไร

มันทำหน้าที่เพียงประกอบคอมโพเนนต์ที่มีอยู่

---

## 5. โฟลเดอร์ `core/`

### บทบาท

โฟลเดอร์ `core/` เก็บ **คำศัพท์ที่ใช้ร่วมกัน** ของโปรเจกต์

มันรวบรวมองค์ประกอบที่หลายเลเยอร์ใช้ร่วมกัน แต่ตัวมันเองไม่ใช่กฎทางธุรกิจ

อาจประกอบด้วย:

- ความสามารถ (capabilities);
- การแจงนับ (enumerations);
- ค่าคงที่;
- ข้อยกเว้นที่ใช้ร่วมกัน;
- ชนิดข้อมูลทั่วไป;
- ข้อมูลแพลตฟอร์ม;
- นิยามของระดับหรือสถานะ

### ตัวอย่าง

```text
core/
├── capabilities.py
├── constants.py
├── enums.py
└── exceptions.py
```

| ไฟล์ | บทบาท |
|---|---|
| `capabilities.py` | อธิบายความสามารถที่มีอยู่หรือเปิดใช้ได้ |
| `constants.py` | เก็บค่าคงที่ของโปรเจกต์ |
| `enums.py` | กำหนดสถานะ ชนิด หรือระดับที่เป็นไปได้ |
| `exceptions.py` | กำหนดข้อผิดพลาดที่ใช้ร่วมกัน |

### กฎ

`core/` ต้องเบาและเสถียร

ต้องไม่มี:

- ตรรกะทางธุรกิจที่ซับซ้อน;
- การเรียกเครือข่าย;
- การเข้าถึงดิสก์;
- โค้ดอินเทอร์เฟซผู้ใช้;
- การพึ่งพาไลบรารีภายนอกโดยตรง

---

## 6. โฟลเดอร์ `domain/`

### บทบาท

โฟลเดอร์ `domain/` คือ **หัวใจของโปรเจกต์**

มันเก็บตรรกะทางธุรกิจล้วน: กฎ แนวคิด และการคำนวณที่กำหนดว่าแอปพลิเคชันทำอะไรจริง ๆ

อาจประกอบด้วย:

- เอนทิตี;
- value object;
- นโยบาย (policies);
- กฎทางธุรกิจ;
- บริการโดเมน;
- การคำนวณ;
- การตรวจสอบความถูกต้องทางธุรกิจ;
- โมเดลข้อมูลทางธุรกิจ

### ตัวอย่าง

```text
domain/
├── entities/
├── value_objects/
├── policies/
└── services/
```

| องค์ประกอบ | บทบาท |
|---|---|
| เอนทิตี | ออบเจกต์ทางธุรกิจที่มีตัวตน (identity) |
| Value object | ค่าที่เปลี่ยนแปลงไม่ได้และผ่านการตรวจสอบแล้ว |
| นโยบาย | กฎทางธุรกิจที่นำกลับมาใช้ได้ |
| บริการโดเมน | ตรรกะทางธุรกิจที่ไม่ได้เป็นของเอนทิตีใดเอนทิตีหนึ่ง |

### กฎที่เข้มงวด

โฟลเดอร์ `domain/`:

- ไม่เข้าถึงดิสก์;
- ไม่เรียกเครือข่าย;
- ไม่รันคำสั่งระบบ;
- ไม่เข้าถึงฐานข้อมูล;
- ไม่ import อินเทอร์เฟซผู้ใช้;
- ไม่ import โครงสร้างพื้นฐาน;
- ไม่พึ่งพาไลบรารีเทคนิคภายนอกเมื่อหลีกเลี่ยงได้

โดเมนต้องทดสอบได้โดยไม่ต้องมีเซิร์ฟเวอร์ ไฟล์ เครือข่าย หรืออินเทอร์เฟซ

---

## 7. โฟลเดอร์ `application/`

### บทบาท

โฟลเดอร์ `application/` ประสานงานกรณีการใช้งาน

มันตอบคำถามว่า:

> “จะเกิดอะไรขึ้นเมื่อผู้ใช้ร้องขอการกระทำนี้?”

ภายในประกอบด้วย:

- commands;
- queries;
- กรณีการใช้งาน;
- ตัวประสานงาน (orchestrators);
- ตัวจัดการการกระทำ (handlers);
- การประสานระหว่างโดเมนกับพอร์ต

### ความแตกต่างระหว่าง commands / queries

| ชนิด | เป้าหมาย | แก้ไขข้อมูล |
|---|---|---|
| Command | ดำเนินการกระทำ | ใช่ |
| Query | อ่านหรือคำนวณข้อมูล | ไม่ |

ตัวอย่าง:

| Command | Query |
|---|---|
| ใช้การตั้งค่า | อ่านการตั้งค่าปัจจุบัน |
| เริ่มการวิเคราะห์ | ดึงผลการวิเคราะห์ |
| ส่งออกรายงาน | แสดงรายการที่มีอยู่ |
| ล้างข้อมูล | ดูประวัติ |

### ตัวอย่าง

```text
application/
├── commands/
│   ├── apply_config.py
│   └── export_report.py
└── queries/
    ├── get_status.py
    └── list_items.py
```

### กฎ

`application/` ไม่มี:

- การแสดงผลในเทอร์มินัล;
- อินเทอร์เฟซ Textual;
- คำสั่ง Rich;
- การเข้าถึงฐานข้อมูลโดยตรง;
- การเรียกเครื่องมือภายนอกโดยตรง

มันประสานงาน แต่ไม่ลงมือทำรายละเอียดทางเทคนิค

---

## 8. โฟลเดอร์ `ports/`

### บทบาท

โฟลเดอร์ `ports/` กำหนด **สัญญา** ที่แอปพลิเคชันคาดหวัง

พอร์ตอธิบาย **สิ่งที่แอปพลิเคชันต้องการ** โดยไม่บังคับว่าต้อง implement อย่างไร

โดยทั่วไปประกอบด้วย:

- `Protocol`;
- คลาสนามธรรม `ABC`;
- อินเทอร์เฟซของ repository;
- อินเทอร์เฟซการส่งออก;
- อินเทอร์เฟซของโพรบ;
- อินเทอร์เฟซของบริการภายนอก;
- อินเทอร์เฟซการจัดเก็บ

### ตัวอย่าง

```text
ports/
├── repositories.py
├── exporters.py
├── probes.py
└── storage.py
```

| พอร์ต | บทบาท |
|---|---|
| `Repository` | อ่านหรือจัดเก็บข้อมูล |
| `Exporter` | สร้างผลลัพธ์ในรูปแบบที่กำหนด |
| `Probe` | เก็บข้อมูลของระบบหรือเครือข่าย |
| `Storage` | จัดการแบ็กเอนด์สำหรับการจัดเก็บถาวร |

### ตัวอย่างเชิงแนวคิด

```python
class ReportExporter(Protocol):
    def export(self, report: Report, destination: Path) -> None:
        ...
```

สัญญานี้บอกว่า:

> “แอปพลิเคชันต้องการออบเจกต์ที่สามารถส่งออกรายงานได้”

มันไม่ได้บอกว่า:

- การส่งออกจะเป็น Markdown หรือไม่;
- การส่งออกจะเป็น JSON หรือไม่;
- ไฟล์จะถูกเขียนลงเครื่องหรือไม่;
- การส่งออกจะถูกส่งผ่านเครือข่ายหรือไม่

การเลือกเหล่านี้เป็นหน้าที่ของ `infrastructure/`

### กฎ

พอร์ตคือสัญญา ไม่ใช่ implementation

ต้องไม่มี:

- ตรรกะทางธุรกิจที่ซับซ้อน;
- การเข้าถึงดิสก์;
- การเรียกเครือข่าย;
- implementation ที่ใช้จริง;
- การพึ่งพาไลบรารีภายนอกโดยตรง

---

## 9. โฟลเดอร์ `infrastructure/`

### บทบาท

โฟลเดอร์ `infrastructure/` เก็บ **implementation ที่ใช้จริง** ของพอร์ต

นี่คือเลเยอร์ที่สื่อสารกับโลกภายนอก

อาจประกอบด้วย:

- การเข้าถึงไฟล์;
- การเข้าถึงฐานข้อมูล;
- การส่งออกเป็น Markdown, JSON, CSV หรือรูปแบบอื่น;
- การบันทึกล็อก;
- การเรียกเครือข่าย;
- โพรบระบบ;
- การรันเครื่องมือภายนอกอย่างมีการควบคุม;
- อะแดปเตอร์สำหรับไลบรารีภายนอก;
- implementation ของ repository;
- implementation ของการจัดเก็บ

### ตัวอย่าง

```text
infrastructure/
├── storage/
│   ├── sqlite_repository.py
│   └── json_file_repository.py
├── export/
│   ├── markdown_exporter.py
│   └── json_exporter.py
├── system/
│   ├── process_probe.py
│   └── filesystem_probe.py
└── logging/
    └── structured_logger.py
```

| องค์ประกอบ | บทบาท |
|---|---|
| `sqlite_repository.py` | implement repository ด้วย SQLite |
| `json_file_repository.py` | implement repository ด้วยไฟล์ JSON |
| `markdown_exporter.py` | ส่งออกรายงานเป็น Markdown |
| `json_exporter.py` | ส่งออกรายงานเป็น JSON |
| `process_probe.py` | เก็บข้อมูลเกี่ยวกับโปรเซส |
| `filesystem_probe.py` | เก็บข้อมูลเกี่ยวกับระบบไฟล์ |
| `structured_logger.py` | สร้างล็อกแบบมีโครงสร้าง |

### กฎ

`infrastructure/` เป็นเลเยอร์เดียวที่ได้รับอนุญาตให้เข้าถึงโดยตรง:

- ระบบไฟล์;
- เครือข่าย;
- SQLite;
- ไลบรารีภายนอก;
- เครื่องมือของระบบ;
- โปรเซสย่อย เมื่อจำเป็นและมีการควบคุม

การรวมศูนย์นี้ช่วยให้:

- ทดสอบได้ง่าย;
- ตรวจสอบความปลอดภัยได้ง่าย;
- เปลี่ยนแบ็กเอนด์ได้ง่าย;
- จำกัดผลข้างเคียง

## 10. โฟลเดอร์ `interfaces/`

### บทบาท

โฟลเดอร์ `interfaces/` เก็บจุดเข้าใช้งานที่ผู้ใช้มองเห็น

มันแยกอย่างชัดเจนระหว่าง:

- CLI;
- TUI;
- อินเทอร์เฟซเว็บหรือ API ที่อาจมีในอนาคต

### โครงสร้าง

```text
interfaces/
├── cli/
│   ├── main.py
│   ├── commands/
│   └── rendering/
└── tui/
    ├── app.py
    ├── screens/
    └── widgets/
```

| อินเทอร์เฟซ | เทคโนโลยี | บทบาท |
|---|---|---|
| `cli/` | Rich | อินเทอร์เฟซบรรทัดคำสั่ง |
| `tui/` | Textual | อินเทอร์เฟซแบบโต้ตอบในเทอร์มินัล |

### CLI

CLI คืออินเทอร์เฟซบรรทัดคำสั่ง

ใช้สำหรับ:

- เปิดแอปพลิเคชัน;
- ดำเนินการกระทำเฉพาะอย่าง;
- แสดงผลลัพธ์;
- ทำงานอัตโนมัติ;
- รวมเครื่องมือเข้ากับสคริปต์;
- ใช้แอปพลิเคชันจากระยะไกลผ่าน SSH

### TUI

TUI คืออินเทอร์เฟซแบบโต้ตอบในเทอร์มินัล

ใช้สำหรับ:

- นำทางระหว่างฟีเจอร์;
- ดูข้อมูล;
- ดำเนินการกระทำ;
- ดูผลลัพธ์;
- ใช้แอปพลิเคชันโดยไม่ต้องจำคำสั่งทั้งหมด

### กฎ

อินเทอร์เฟซไม่มีตรรกะทางธุรกิจ

หน้าที่ของมันคือ:

- รับความต้องการของผู้ใช้;
- เรียกกรณีการใช้งานใน `application/`;
- แสดงผลลัพธ์;
- แปลข้อผิดพลาดเป็นข้อความที่เข้าใจได้

มันต้องไม่:

- เรียกโครงสร้างพื้นฐานโดยตรง;
- รันโปรเซสย่อย;
- เข้าถึงไฟล์โดยตรง;
- มีกฎทางธุรกิจ;
- ทำซ้ำตรรกะของ `application/`

## 11. โฟลเดอร์ `plugins/`

### บทบาท

โฟลเดอร์ `plugins/` สงวนไว้สำหรับ **ส่วนขยายที่ติดมาในตัว**

ช่วยให้เพิ่มฟีเจอร์ได้โดยไม่ทำให้แกนหลักของโปรเจกต์หนักขึ้น

ตัวอย่างเช่น ปลั๊กอินอาจ:

- เพิ่มรูปแบบการส่งออก;
- เพิ่มโพรบ;
- เพิ่มคำสั่ง;
- เพิ่มหน้าจอ TUI;
- เพิ่มการเชื่อมต่อภายนอก;
- เพิ่มความสามารถเสริม

### หลักการ

ปลั๊กอินต้องปฏิบัติตามกฎเดียวกับส่วนอื่นของโปรเจกต์:

- ไม่ข้ามพอร์ต;
- ไม่แก้ไขโดเมนโดยตรง;
- เปิดให้ใช้ฟีเจอร์ผ่านสัญญาที่ชัดเจน;
- ปิดใช้งานได้โดยไม่ทำให้แอปพลิเคชันเสียหาย

### โครงสร้างที่เป็นไปได้

```text
plugins/
└── [plugin_name]/
    ├── __init__.py
    ├── manifest.py
    ├── application/
    ├── infrastructure/
    └── interfaces/
```

### กฎ

ปลั๊กอินคือส่วนขยาย ไม่ใช่ประตูหลัง

มันต้องเคารพสถาปัตยกรรมโดยรวม และต้องไม่สร้างการพึ่งพาแบบวนกับแกนหลักของโปรเจกต์

---

## 12. โฟลเดอร์ `shared/`

### บทบาท

โฟลเดอร์ `shared/` เก็บยูทิลิตีที่ใช้ร่วมกันซึ่งไม่ได้เป็นของโดเมน แอปพลิเคชัน หรือโครงสร้างพื้นฐาน

มันรวบรวมฟังก์ชันทั่วไปที่นำกลับมาใช้ได้

อาจประกอบด้วย:

- การแยกวิเคราะห์ (parsing);
- ยูทิลิตีเครือข่าย;
- การจัดรูปแบบ;
- การจัดการข้อความ;
- ตัวช่วยด้านวันที่;
- ตัวช่วยด้านพาธ;
- ยูทิลิตีตรวจสอบความถูกต้องทั่วไป;
- ตัวช่วยการแปลงข้อมูล (serialization)

### ตัวอย่าง

```text
shared/
├── parsing/
├── network/
├── formatting/
└── utils/
```

| โฟลเดอร์ | บทบาท |
|---|---|
| `parsing/` | วิเคราะห์ข้อความ JSON YAML หรือรูปแบบอื่น |
| `network/` | ยูทิลิตีเครือข่ายทั่วไป |
| `formatting/` | จัดรูปแบบค่า วันที่ ขนาด หรือตาราง |
| `utils/` | ฟังก์ชันยูทิลิตีที่ใช้ร่วมกัน |

### กฎ

`shared/` ต้องไม่กลายเป็นโฟลเดอร์รวมของจิปาถะ

ยูทิลิตีควรอยู่ใน `shared/` ก็ต่อเมื่อมัน:

- นำกลับมาใช้ได้;
- เป็นแบบทั่วไป;
- ไม่ขึ้นกับกรณีการใช้งานเฉพาะ;
- มีประโยชน์ต่อหลายเลเยอร์

## 13. สรุปหน้าที่

| โฟลเดอร์ | บทบาทหลัก | พึ่งพาได้ | ต้องไม่พึ่งพา |
|---|---|---|---|
| `app/` | ประกอบและเริ่มแอปพลิเคชัน | ทุกเลเยอร์ | — |
| `core/` | คำศัพท์ ค่าคงที่ enum และข้อยกเว้น | `shared/` หากจำเป็น | `infrastructure/`, `interfaces/` |
| `domain/` | ตรรกะทางธุรกิจล้วน | `core/` | `application/`, `infrastructure/`, `interfaces/` |
| `application/` | ประสานงานกรณีการใช้งาน | `domain/`, `ports/`, `core/` | `infrastructure/`, `interfaces/` |
| `ports/` | กำหนดสัญญา | `domain/` หากจำเป็น | `infrastructure/`, `interfaces/` |
| `infrastructure/` | implement พอร์ตและสื่อสารกับภายนอก | `ports/`, `domain/`, `core/`, `shared/` | `interfaces/` |
| `interfaces/` | โต้ตอบกับผู้ใช้ | `application/`, `core/` | `infrastructure/` โดยตรง |
| `plugins/` | เพิ่มส่วนขยาย | ขึ้นกับชนิดของส่วนขยาย | การข้ามสถาปัตยกรรม |
| `shared/` | ยูทิลิตีที่ใช้ร่วมกัน | ไม่มีเลเยอร์ธุรกิจใด | ตรรกะทางธุรกิจเฉพาะ |

## 14. ตัวอย่างลำดับการทำงานของการกระทำ

สมมติว่าผู้ใช้ร้องขอให้ส่งออกรายงานเป็น Markdown

```text
1. ผู้ใช้รันคำสั่ง CLI

2. interfaces/cli/
   รับคำสั่งและตัวเลือก

3. interfaces/cli/
   เรียกกรณีการใช้งานที่ตรงกันใน application/

4. application/
   ตรวจสอบความต้องการและเตรียมการกระทำ

5. application/
   ใช้โดเมนเพื่อสร้างหรือตรวจสอบรายงาน

6. application/
   ร้องขอการส่งออกผ่านพอร์ต ReportExporter

7. infrastructure/
   จัดหา implementation MarkdownExporter

8. infrastructure/
   เขียนไฟล์ Markdown ลงดิสก์

9. interfaces/cli/
   แสดงผลลัพธ์ให้ผู้ใช้
```

แผนภาพอย่างง่าย:

```text
CLI
 ↓
Application
 ↓
Domain
 ↓
Port Exporter
 ↓
Infrastructure Markdown
 ↓
ไฟล์ Markdown
```

## 15. ทำไมต้องใช้สถาปัตยกรรมนี้?

### อ่านง่าย

แต่ละโฟลเดอร์มีบทบาทเดียว จึงหาได้ง่ายว่าต้องเพิ่มหรือแก้ฟีเจอร์ที่ไหน

### ทดสอบได้

โดเมนทดสอบได้โดยไม่ต้องมีอินเทอร์เฟซ ฐานข้อมูล หรือการเข้าถึงเครือข่าย

### ดูแลรักษาง่าย

การเปลี่ยนอินเทอร์เฟซ การจัดเก็บ หรือเครื่องมือภายนอก ต้องไม่ทำให้ต้องเขียนตรรกะทางธุรกิจใหม่

### ความปลอดภัย

การเข้าถึงที่อ่อนไหว — ไฟล์ เครือข่าย โปรเซสย่อย ฐานข้อมูล — รวมอยู่ใน `infrastructure/` ทำให้ตรวจสอบและควบคุมได้ง่ายขึ้น

### ขยายต่อได้

สามารถเพิ่ม:

- อินเทอร์เฟซใหม่;
- รูปแบบการส่งออกใหม่;
- แบ็กเอนด์การจัดเก็บใหม่;
- ปลั๊กอินใหม่;
- โพรบระบบใหม่;

โดยไม่ต้องแก้ไขแกนธุรกิจ

### พกพาได้

แอปพลิเคชันสามารถพัฒนาไปสู่สภาพแวดล้อม ระบบ หรือรูปแบบการโต้ตอบอื่นได้ โดยไม่ผูกติดกับเทคโนโลยีใดเทคโนโลยีหนึ่ง

## 16. กฎที่ควรจำ

- โดเมนบริสุทธิ์
- แอปพลิเคชันประสานงาน
- พอร์ตประกาศความต้องการ
- โครงสร้างพื้นฐาน implement
- อินเทอร์เฟซแสดงผลและรับข้อมูล
- `app/` ประกอบ
- `core/` และ `shared/` ให้คำศัพท์และยูทิลิตีที่ใช้ร่วมกัน
- ปลั๊กอินขยายความสามารถโดยไม่ข้ามสถาปัตยกรรม

สรุปในประโยคเดียว:

> **แอปพลิเคชันแยกสิ่งที่มันทำ วิธีที่มันทำ และวิธีที่ผู้ใช้ใช้งานมันออกจากกัน**
